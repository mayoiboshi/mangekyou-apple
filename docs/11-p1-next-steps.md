# 11 — 下一轮语义研究的入口

本轮完成的是 P1 静态基础，不是完成 P1 全部语义调查，更不是完成移植。`readiness.json` 的本轮 verified 与 `runtime_development_ready=false` 并存，含义不同。

现在已能按字节定位、保留全部包版本和排版、拆出行内候选、比较文本差异，并检查真实复合资源。下一轮不再以“能不能取出台词”作为主要问题，应围绕以下阻塞逐项形成可审查的语义契约。

| 顺序 | 研究对象 | 可先使用的证据 | 必须保留的未知 |
|---|---|---|---|
| 1 | 11 组真实文本差异和加载优先级 | 逐包来源、差分行区间、词法字段摘要 | 哪个版本实际生效；纯净发行版与汉化层区别 |
| 2 | 标签、调用/返回、条件与循环 | 3,106 个标签字面引用、205 个非字面目标样式 | 大小写、前导 !、局部/全局、参数和返回约定 |
| 3 | 变量与表达式 | 2,306 声明样式、实际类型拼写、源代码位置 | 整数宽度、溢出、字符串、列表、表、生命周期及存档域 |
| 4 | 模板与资源查找 | 156 定义样式、4,919 美元前缀引用、18,786 资源候选 | 替换次序、数值/宏歧义、默认目录/扩展名、动态组合 |
| 5 | ABMP 运行数据 | 17 容器、48 成员和未知参数范围 | 18 个 Unknown 载体、参数含义、动画时间与图层 |
| 6 | 存档与演出状态 | 已定位的系统脚本引用和 P0 清单 | 实际状态模型、序列化结构、恢复点及原引擎一致性 |

语义契约至少应写明触发语法、字段类型、状态读取/写入、可能的跳转、异常输入行为、证据与反例。缺少证据的契约只能是 Hypothesis，不能变成默认执行行为。

优先从可在脚本定义和多个使用点相互约束的机制入手，区分“脚本本身表达了什么”与“原引擎实际如何执行”。如果静态材料仍不足，再提出具体的对照实验及所需授权；本次没有执行原引擎、Wine 或汉化程序，也没有产生可玩的简化替代品。

原生核心语言继续不定。本轮的 Python 取证工具与 P0 的 ARM64 Rust 文本导出只证明工具链可运行，没有完成性能、渲染依赖、跨平台接口或许可证选型。不得因为已使用某种语言编译工具，就据此锁定最终运行时。

本轮未将游戏数据发往外部服务；原始 PACK 摘要与 P0 相同，P0 JSON 报告逐个摘要保持不变。已有研究副本只读使用，新的完整 IR 仅在忽略目录，公开结果只含统计、标识符、摘要及来源范围。
